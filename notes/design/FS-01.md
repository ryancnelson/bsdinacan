# FS-01 design: `truncate(2)` and `ftruncate(2)`

Status: design review only. No runtime code in this branch. This document is
the deliverable requested before `FS-01`'s backlog status can move from
"Blocked pending design review" to `Ready`.

## 1. What already exists (read before changing anything)

- `struct cb_ramfs_node` (`src/ramfs.c:9`) stores a regular file as
  `unsigned char *data`, `size_t size` (logical length), `size_t capacity`
  (allocated length, always `>= size`). `size` and `capacity` are
  independent: shrinking never has to reallocate, and growth reuses spare
  capacity from a prior larger size without zeroing it again (`node_write`,
  `src/ramfs.c:336`).
- `node_write` (`src/ramfs.c:336`) already implements the two behaviors this
  slice must generalize:
  - **Lazy hole-zeroing**: `if (start > node->size) memset(node->data +
    node->size, 0, start - node->size);` — zeroes the gap only when a later
    write actually reaches past it.
  - **Capacity-growth zeroing**: when `cb_resize` grows the buffer, the new
    tail `[old capacity, new capacity)` is memset to zero immediately
    (`src/ramfs.c:375`), because that memory has never been initialized at
    all (unlike the logical `[size, capacity)` gap left by a shrink, which
    was previously real data and must be re-zeroed by whichever write or
    truncate reaches it next).
  - **Resize-failure atomicity**: `cb_resize` returning `NULL` sets `ENOMEM`
    and returns before touching `node->data`/`node->size` — the old
    allocation and its contents remain valid and unchanged.
- `ramfs_open` (`src/ramfs.c:227`) already special-cases `O_TRUNC`: `if
  ((flags & CB_O_TRUNC) && (flags & CB_O_ACCMODE) != CB_O_RDONLY) node->size
  = 0;` — a bare metadata write, no buffer touched. This slice's `ftruncate`
  reuses the same one-line shrink for the shrink-to-any-size case; only
  growth needs new logic.
- Directories can never be opened as file descriptors at all —
  `ramfs_open` already rejects `CB_NODE_DIRECTORY` with `EISDIR`
  (`src/ramfs.c:227`-`228`). So `ftruncate(fd, ...)` can never observe a
  directory; only path-based `truncate(path, ...)` can.
- Non-seekable descriptors (pipes, terminals) share one stub, `no_seek`
  (`src/core.c:282`), which every such `cb_file_ops.lseek` slot points at
  instead of `NULL`; it unconditionally sets `CB_ESPIPE`. The dispatch
  function (`api_lseek`, `src/core.c:903`) additionally treats a genuinely
  `NULL` ops slot as `EBADF`, as a defensive fallback for a descriptor type
  that does not define the operation at all. `truncate` should follow this
  exact two-layer pattern rather than invent a new error convention.
- `stat`/`fstat` (`src/core.c:1036`, `1017`; `src/vfs.c:259`) are the
  existing path-vs-descriptor pair to model `truncate`/`ftruncate` on:
  `cb_vfs_stat_path` resolves a path to a node and calls a generic,
  versioned `node->ops->stat`; `api_fstat` dispatches through the
  per-open-file `file->ops->stat`. Two new ABI operations, not one
  flag-driven operation, matches this precedent.
- Permission-bit enforcement is deferred project-wide (SPEC.md §7: "ownership
  enforcement... deferred"). Nothing anywhere checks a stat mode bit before
  allowing a write, unlink, or mkdir. `truncate`'s "path-versus-descriptor
  permissions" question is therefore **not** about `mode` bits at all — it
  is about the one access check that already exists and already
  distinguishes the two entry points:
  - `ftruncate(fd, ...)`: the fd carries `CB_O_ACCMODE` from its own
    `open()` call. `node_write` already refuses a `CB_O_RDONLY` fd with
    `EBADF` (`src/ramfs.c:344`); `ftruncate` must apply the identical check,
    for the identical reason (a write-class operation on a read-only
    handle), using the identical errno.
  - `truncate(path, ...)`: there is no fd and therefore no access mode to
    consult. The only applicable check is the node's *type* — regular file
    vs. directory — exactly like `cb_vfs_stat_path` has no access check
    either, only a type-implied one (you cannot `open()` a directory to
    begin with).
- No `off_t` typedef exists anywhere in `libc/include/` today (only
  `cb_ssize_t`/`ssize_t`, in `unistd.h`). This is a genuine prerequisite,
  not a design choice — see §7.

## 2. Storage-model behavior for growth and shrink

Both `truncate` and `ftruncate` end up calling the same new generic node
operation, `cb_vfs_node_ops.truncate(node, new_size)` (§4), which is the one
place resize logic lives. Behavior, entirely in terms of the existing
`size`/`capacity`/`data` triple:

- **Shrink** (`new_size <= node->size`): `node->size = new_size;` only.
  `capacity` and `data` are untouched — no reallocation, no zeroing. This is
  deliberately identical to the existing `O_TRUNC`-to-zero special case,
  generalized to an arbitrary target size. Bytes beyond the new `size`
  remain physically present in `data` but are logically unreachable: reads
  are bounded by `node->size` (`node_read`, `src/ramfs.c:312`), and if a
  later write or truncate-growth reaches past the new (shrunk) `size`, the
  existing lazy-hole-zero logic in `node_write` already re-zeros that exact
  span — **this is why shrink-then-grow-via-write needs no new code at
  all**, only shrink-then-grow-via-*truncate* does (next bullet).
- **Grow** (`new_size > node->size`): unlike `node_write`'s *lazy*
  hole-zeroing (deferred until a write actually reaches the gap), a bare
  `truncate`/`ftruncate` grow has no accompanying write to defer to — a
  `read()` immediately afterward, with no intervening write, must already
  observe zeros over `[old size, new size)`. So growth via truncate must
  **eagerly** zero that entire span in `data`, not just the newly-resized
  tail:
  1. If `new_size > node->capacity`, `cb_resize` up (reusing `node_write`'s
     existing capacity-doubling policy is not required here — a single
     resize to exactly `new_size`, or to the same doubling policy, are both
     acceptable; recommend reusing the doubling policy so a
     truncate-then-write-a-little-more doesn't immediately force a second
     resize). On resize failure: `ENOMEM`, `node->size`/`capacity`/`data`
     completely unchanged (matching `node_write`'s existing atomicity).
  2. Zero the entire span `[old_size, new_size)` in `data` — this covers
     both sub-cases at once: bytes in `[old_size, old_capacity)` are stale
     real data from before a prior shrink (must be re-zeroed now, since nothing
     else will), and bytes in `[old_capacity, new_capacity)` are freshly
     allocated (must be zeroed because they were never initialized). A
     single `memset(data + old_size, 0, new_size - old_size)` after any
     resize handles both; do not rely on `cb_resize`/`cb_allocate`'s
     internal zeroing of *newly grown* capacity alone, because that by
     itself does **not** cover the stale-post-shrink sub-case.
  3. `node->size = new_size;`

## 3. Offsets, shared descriptors, and append

- `cb_off_t offset` lives on `struct cb_open_file`, not on the node. `dup`/
  `dup2` share the *same* `cb_open_file` (SPEC §6), so they automatically
  share one offset; truncate never touches offset at all, on any path. This
  needs **zero new code** — it falls out of the existing object graph. Test
  matrix item: shrink a file out from under an offset that was already
  past the new end; the fd's offset field is bit-for-bit unchanged, a
  `read()` there returns `0` (EOF, per existing `node_read` bounds check),
  and a `write()` there zero-fills the hole up to the write position (existing
  `node_write` logic, no new code, but must be covered by a regression test
  since this is the first feature that can *produce* such a hole without a
  write first creating it).
- A **second, independent** `open()` of the same path — a different
  `cb_open_file`, different offset, but the *same* retained
  `cb_ramfs_node` (existing reference-counting: `ramfs_node_retain` in
  `ramfs_open`, `src/ramfs.c:234`) — must observe the new size immediately
  via `fstat`, because `size` lives on the shared node. Test matrix item
  covers this as the real "no per-descriptor caching" proof, and per
  AGENTS.md should be exercised across two *tasks* (not just two fds in one
  task) with forced cooperative interleaving, matching how `PENV-01`/`PENV-03`
  proved task-local vs. shared state elsewhere in this codebase — here the
  point is the reverse: this state must **not** be task-local, it must be
  genuinely shared through the VFS node regardless of which task's
  descriptor reaches it.
- **Append interaction is already correct with no new code.** `node_write`
  re-reads `node->size` fresh on every call when `CB_O_APPEND` is set
  (`file->offset = (cb_off_t)node->size;`, `src/ramfs.c:352`) — since
  truncate changes `node->size` directly, the very next append-mode write
  after a truncate (grow or shrink) lands at the *new* end, automatically.
  This is a regression-test item, not an implementation item: confirm it,
  don't build it.

## 4. Versioned API/ABI additions

Two new `cb_api_v1` operations, named after the existing `stat`/`fstat`
path-vs-descriptor pair:

```c
int (*truncate)(const char *path, cb_off_t length);
int (*ftruncate)(int fd, cb_off_t length);
```

Per AGENTS.md, these are **appended after whatever is currently the last
field** in `cb_api_v1` (`getopt_state_location`, as of `78a1e5b`) — not
inserted near `stat`/`unlink` despite the logical grouping; struct order is
an ABI-append concern, not a readability concern.

One new generic, versioned VFS node operation (`struct cb_vfs_node_ops`,
`src/internal.h:96`), appended after `name`:

```c
int (*truncate)(struct cb_vfs_node *node, cb_off_t new_size);
```

This is the *one* place resize logic lives (§2). RAMFS implements it against
its own private `cb_ramfs_node` fields. Both call paths below reach it:

- `truncate(path, length)`: new `cb_vfs_truncate_path` in `src/vfs.c`,
  written like `cb_vfs_stat_path` (`src/vfs.c:259`) — normalize, resolve,
  then instead of `node->ops->stat(...)`: reject `CB_NODE_DIRECTORY` with
  `EISDIR`, else call `node->ops->truncate(node, length)`.
- `ftruncate(fd, length)`: one new `cb_file_ops` slot (`src/internal.h:129`),
  appended after `last_close`:

  ```c
  int (*truncate)(struct cb_open_file *file, struct cb_task *task, cb_off_t new_size);
  ```

  RAMFS's regular-file implementation checks `CB_O_ACCMODE != CB_O_WRONLY/
  CB_O_RDWR` (same test as `node_write`, same `EBADF`), then delegates to
  `file->object.node->ops->truncate(...)` — no duplicated resize logic.
  Pipes and terminals get a new shared stub, `no_truncate` (`src/core.c`,
  next to `no_seek`), which sets `CB_ESPIPE` and returns `-1`, wired into
  `console_input_ops`, `console_output_ops`, and both pipe
  direction tables — mirroring `no_seek` exactly rather than inventing a
  different errno for "non-seekable-shaped" operations. The dispatch
  function `api_ftruncate` additionally treats a genuinely `NULL`
  `ops->truncate` as `EBADF`, matching `api_lseek`'s existing defensive
  fallback.

Error taxonomy (all values already exist in `enum cb_error`,
`include/cannedbsd/abi.h`):

| Case | Errno | Precedent |
|---|---|---|
| `truncate` target is a directory | `CB_EISDIR` | `ramfs_open`'s existing directory-open rejection |
| `ftruncate` on a read-only fd | `CB_EBADF` | `node_write`'s existing `CB_O_RDONLY` rejection |
| `ftruncate` on a pipe or terminal fd | `CB_ESPIPE` | `no_seek`'s existing precedent for non-seekable descriptors |
| `ftruncate`/`truncate` on an fd/ops slot that doesn't define `truncate` at all | `CB_EBADF` | `api_lseek`'s existing `NULL`-ops defensive fallback |
| negative `length` | `CB_EINVAL` | `node_lseek`'s existing negative-result rejection |
| `length` too large to represent as `size_t` on this host | `CB_EINVAL` | `api_read`/`api_write`'s existing `count > INT64_MAX` dispatch-layer guard (same "magnitude too large to represent" class, not the arithmetic-sum-overflow class that legitimately uses `ENOSPC` in `node_write`) |
| allocation failure while growing | `CB_ENOMEM` | `node_write`'s existing `cb_resize`-failure handling; old `size`/`capacity`/`data` must remain valid and unchanged, verified by a subsequent read |

## 5. Libc surface (prerequisite + wrappers)

**Prerequisite, not part of this slice's own scope, but blocking it:** no
`off_t` typedef exists in `libc/include/` yet. Add
`typedef cb_off_t off_t;` to `libc/include/unistd.h` (co-located with the
existing `typedef cb_ssize_t ssize_t;`) before `truncate`/`ftruncate` can be
declared with their real POSIX signatures. This is a one-line addition, not
a new subsystem, but it must land (in this PR or immediately before it)
since neither function can be prototyped without it.

Ordinary-facing declarations, `libc/include/unistd.h` (POSIX places both
here, not in `sys/stat.h` — no such header exists in this project and none
is needed for this slice):

```c
int cb_libc_truncate(const char *path, off_t length);
int cb_libc_ftruncate(int fd, off_t length);
#define truncate cb_libc_truncate
#define ftruncate cb_libc_ftruncate
```

Private declarations in `include/cannedbsd/libc.h`, thin wrappers in
`libc/cb_libc.c` delegating to `bound_api->truncate`/`bound_api->ftruncate`
— the same one-line-forwarding shape as every existing `cb_libc_*` wrapper
(e.g. `cb_libc_close`, `libc/cb_libc.c`). `api_is_usable` gains
`api->truncate != NULL && api->ftruncate != NULL`, matching the existing
per-operation-group style there.

## 6. Falsifiable test matrix

Ordinary-source red/green pair, following the `PENV-01`/`PENV-02`/`PENV-03`
pattern exactly: a new `tests/libc_truncate_probe.c` (ordinary main, no
cannedBSD names, compiled separately with `-Dmain=...`, linked into
`build/test_core`) referencing `truncate`/`ftruncate` gives the required red
— compiles clean (once `off_t` exists and the header declarations are in
place), fails to **link** (`undefined reference to 'cb_libc_truncate'`/
`'cb_libc_ftruncate'`) until the veneer and ABI wiring exist. This matches
`FS-01`'s own backlog wording ("ordinary truncate/ftruncate probes fail to
compile") in spirit the same way `PENV-02`/`PENV-03`'s literal "fails to
link" reds did — the interface is declared as part of establishing red, only
the definition is missing.

Raw-ABI orchestrator test(s) in `tests/test_core.c`, covering:

1. **Shrink**: write 100 bytes, `ftruncate` to 10, `fstat` reports size 10,
   read returns exactly the first 10 original bytes.
2. **Zero-filled growth, no intervening write**: `ftruncate` from 10 up to
   100 with no write in between; read the full 100 bytes back and confirm
   bytes `[10, 100)` are all zero. This is the one behavior with no
   existing precedent to fall back on (§2) — the test that would fail if
   growth were implemented as a bare `size` bump without eager zeroing.
3. **Shrink-then-grow reuses stale capacity correctly**: write 100 bytes,
   `ftruncate` to 10 (shrink, no reallocation), `ftruncate` back up to 50
   (grow within the *already-allocated* old capacity — capacity was never
   reduced in step 2). Read bytes `[10, 50)` and confirm zero, not the
   original bytes 10–50 from before the shrink. This is the specific
   stale-data leak this design forbids in §2 step 2; a naive
   "only zero newly-`cb_resize`d capacity" implementation would pass test 2
   but fail this one.
4. **Offset untouched by shrink; write past shrunk end zero-fills the
   hole**: open, write 100 bytes, seek to 80, `ftruncate` to 10 (offset
   field must remain 80, unchanged), `read()` at offset 80 returns 0 (EOF),
   then `write()` at offset 80 succeeds and a subsequent read of
   `[10, 80)` is zero and `[80, 80+n)` is the new data — exercising the
   *existing* `node_write` lazy-hole path with a hole this feature is the
   first to be able to create without a prior write.
5. **`CB_O_APPEND` after truncate lands at the new end**: open
   append-mode, write, `ftruncate` (grow or shrink) from a *different* fd
   on the same path, then write again through the append-mode fd; new data
   must land exactly at the post-truncate size, not the pre-truncate one.
6. **Independent open sees the new size, across two tasks**: task A holds
   an open fd on `/tmp/x` and blocks (forced past pipe capacity, the
   established `PENV-01` mechanism); while blocked, task B independently
   `open()`s `/tmp/x` fresh, `ftruncate`s it, and `fstat`s to confirm the
   new size; task A resumes and its own `fstat` also reports the new size
   — proving the change is genuinely on the shared VFS node, not cached
   per-descriptor or per-task.
7. **`dup`'d descriptors observe an `ftruncate` issued through either
   copy** — trivially true since they share one `cb_open_file`, but still
   worth a direct assertion since it is part of the accept criteria.
8. **Errors**: `truncate("/tmp")` (a directory) → `EISDIR`. `ftruncate` on
   an `O_RDONLY` fd → `EBADF`. `ftruncate` on a pipe fd and on a terminal fd
   (fd 0/1) → `ESPIPE`. `ftruncate`/`truncate` with a negative length →
   `EINVAL`. A length deliberately chosen to exceed what fits in this
   host's `size_t` (if `size_t` is narrower than `cb_off_t`'s 64 bits;
   document as host-dependent, still assert on hosts where it applies) →
   `EINVAL`.
9. **Allocation-failure atomicity**: using the existing test-harness
   controlled-allocator hooks (`resize_failure_countdown`, already used by
   e.g. the realloc tests), force `cb_resize` to fail during a growing
   `ftruncate`; assert the call returns `-1`/`ENOMEM` and a subsequent
   `fstat` + read prove `size`, `capacity`, and every existing byte are
   completely unchanged.

## 8. Prerequisites and sequencing

- **Blocking, in-scope-of-this-PR prerequisite**: the `off_t` typedef in
  `libc/include/unistd.h` (§5). Nothing else in the backlog currently
  defines it, and no other Ready item depends on `FS-01` landing it first,
  so it can move with this change rather than needing its own iteration.
- **Not blocking**: `VFS-02` (runtime-visible executable nodes) and `VFS-03`
  (directory iteration/`dirent`) are unrelated areas of the same file
  (`src/vfs.c`) and do not touch `cb_vfs_node_ops.truncate` or
  `cb_ramfs_node`'s size/capacity fields; no ordering constraint either way.
  Checked every worktree actually in flight at review time
  (`PENV-01`..`PENV-04`, `VFS-01`, `PORT-01`, `MAC-01`..`MAC-04`) against
  `origin/main` for touches to `src/ramfs.c`, `src/internal.h`, and
  `src/core.c` (the three files this slice needs). None touch
  `src/ramfs.c`. Two are worth flagging explicitly rather than assuming
  clear:
  - **`work/PORT-01`** edits `src/core.c` in the immediate vicinity of
    `no_seek` (around line 292–307 on its base) as part of a broader
    host-adapter-conformance change. This slice's new `no_truncate` stub is
    deliberately placed "next to `no_seek`" (§4) — whoever implements this
    should re-diff against `PORT-01`'s actual merged state first, since a
    line-adjacent addition to the same function is exactly the shape of
    change most likely to produce a textual (not semantic) merge conflict.
    Not a design blocker, just a sequencing note: land after `PORT-01`
    integrates, or expect to resolve a trivial adjacency conflict.
  - **`work/VFS-01`** adds `struct cb_vfs_mount_entry`, a `mounts[4]`/
    `mount_count` pair on `cb_kernel`, and `cb_vfs_mount_path` to
    `src/internal.h` — a different struct (`cb_kernel`, not
    `cb_vfs_node_ops`/`cb_file_ops`) and a different region of the file, so
    no line-level overlap expected, but both branches are independently
    appending to `src/internal.h` and should each re-verify after the other
    integrates.
  - `PENV-03` (this session's own prior work) also appends to
    `src/internal.h`/`src/core.c` (a `cb_getopt_state_v1` field and its
    accessor) in yet another region (near `errno_location`/
    `environ_location`); same low-risk "different region, re-verify after
    integration" note applies.
- **Scope explicitly not claimed by this slice** (would be speculative
  surface per `AGENTS.md`): `posix_fallocate`, sparse-file `stat` block
  counts, any interaction with hard links (deferred project-wide per
  SPEC.md §7), and any host-mount or persistent-filesystem backend —
  `cb_vfs_node_ops.truncate` is a generic, versioned slot precisely so a
  future non-RAMFS mount can implement or reject it independently.
