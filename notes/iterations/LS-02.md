# LS-02: pinned NetBSD `ls` import, retiring the LS-01 stand-in

- **Status:** Done. Full `make ci` green (normal, sanitizer, isolation builds)
  in Alpine; mac68k reported separately from the Woodpecker API per the
  coordinator's standing instruction (see the completion report, not this
  file, for that evidence).
- **Base:** `origin/main` at `e6dcb3d` (post-`FS-STAT-01`).
- **Branch:** `work/LS-02`.
- **Scope:** import `bin/ls/{ls.c,ls.h,print.c,cmp.c,extern.h,util.c}`
  byte-for-byte (SHA-256/UPSTREAM.md entries below), retire the
  cannedBSD-owned `commands/ls.c` (`LS-01`) in the same commit, and build
  everything `FTS-CHILDREN-01` (folded into this same effort per
  `BACKLOG.md`'s framing, not landed as a separate ID) and real `ls`
  behavior actually needs on top of what `FS-STAT-01`/`FTS-CORE-01`
  already provide.

## Why this was the last real gap in the milestone

Before this ID, `ls -l /` was a usage error (exit 1) and the DEFAULT `ls`
invocation was a single-column, unsorted, option-free stand-in — meaning
the milestone's own claim of "using unchanged NetBSD utilities" could not
be made while the LIST verb was served by an owned substitute. This ID
measured what was actually blocking that (a working `fts_children()`, real
per-file metadata, and formatter gaps), fixed each one, and only then
imported the real source.

## FTS-CHILDREN-01: snapshot + cursor, not a second traversal

`ls.c`'s own `traverse()`/`display()` calls `fts_children(ftsp, 0)` (depth
0: preview the `path_argv` list itself) and `fts_children(ftsp, ch_options)`
per descended directory, then still expects the ordinary `fts_read()` loop
to yield those same entries again for real descent -- a "peek without
disturbing the main traversal" contract `FTS-CORE-01`'s original
`fts_open`/`fts_read`/`fts_close`/`fts_set` did not need to solve.

Solved in `libc/cb_fts.c` via a snapshot + cursor design:
- `cb_libc_fts_children()` drains a directory (or previews `path_argv` at
  depth 0) into a linked list (`children_snapshot`/`next_child` on `struct
  cb_fts_frame`, `root_children` on `struct cb_fts`) using a new
  `classify_peek()` -- stats and resolves `FTS_D` vs `FTS_DNR` via
  open-then-immediately-close, never keeping a directory open or pushing a
  frame the way the real, descending `classify()` does.
- `cb_libc_fts_read()`'s main loop checks `top->next_child` first: if the
  snapshot already drained this directory, it consumes from there instead
  of calling `cb_libc_readdir()` again (which would only see EOF, since the
  snapshot already exhausted the handle), calling the REAL `classify()` at
  actual consumption time so a previewed directory still gets opened and
  pushed for real descent. `rm`/`cp` never call `fts_children()`, so
  `next_child` stays `NULL` for them always -- this is purely additive.
- `FTS_SEEDOT` synthesizes `.`/`..` first when set, matching real fts(3).
- `fts_close()`/the `FTS_SKIP` branch both free whatever a snapshot never
  got consumed (`free_child_list()`), so a `fts_children()` preview that's
  never fully walked doesn't leak.

**A second, real gap found only once `ls.c` itself was measured against
it:** `fts_open()`'s `compar` callback (`ls.c` passes `mastercmp`) was
accepted and stored but never actually applied -- `rm.c`/`cp.c` both pass
`NULL`, so this was invisible until a consumer that sorts arrived. Fixed by
sorting `cb_libc_fts_children()`'s returned list with a real linked-list
merge sort (not `qsort(3)` over a temporary array: this project's libc
veneer has no `qsort`, and RAMFS directories are small enough that adding
one only for this single internal use would be pure overhead) whenever
`fts->compar` is non-`NULL`. Verified this is real, not incidental: files
created out of alphabetical order (`zeta`, `alpha`, `mid`) list back
alphabetically by default and in raw creation order under `-f`.

## The printf/fprintf formatter's further extension

`FORMAT-01` added bounded `%Nd`/`%Ns`. Measuring `print.c`'s actual column
output (`"%*"PRIu64" "`, `"%*llu "`, `"%*lu "`, `"%-*s  "`, `"%*lld, %*lld "`,
`"total %llu\n"`, `"%'*llu "`/`"total %'llu\n"` for `-M`) showed that scope
insufficient for a second consumer. Added to `format_output`
(`libc/cb_libc.c`), extended only as far as these real call sites need:

- Dynamic width (`%*d`/`%*s`/...), bounded 1-32 same as the literal-digit
  form, read via `va_arg(int)` before the conversion itself.
- Left-justify (`%-*s`): only valid on `%s` (no real caller needs a
  left-justified integer); pads after the text instead of before.
- Length modifiers `l`/`ll` for both `%d` and a new `%u` conversion.
- The `'` thousands-separator flag, valid only on `%u` (matching every real
  call site): groups digits by 3 from the right with real comma insertion,
  not merely accepted-and-ignored syntax -- `print.c`'s own `printf()`
  calls under `-M` `(void)`-discard their return value, so silently
  swallowing the conversion (the honest-EINVAL default for anything
  unsupported) would have produced silently incomplete columns rather than
  a visible failure.
- A separate, simpler `cb_libc_snprintf` (not reusing `format_output`'s
  descriptor-based `add_output`) for `ls.c`'s own `snprintf()` call sites
  (`%s`/`%d`/`%u`/`%lld`/`%llu`, no width -- that's all they use).

`%u` becoming a real, supported conversion retired an old design boundary:
`tests/libc_format_probe.c`'s `bad[]` table, `tests/libc_stdio_source.c`,
and `tests/libc_stdio_state_probe.c` each had a "bare `%u` must EINVAL"
probe predating any real consumer. Left-justify's width-source-agnostic
implementation also incidentally validated `%-4s` (literal width, not just
`%-*s`) -- not a deliberately added feature, just a natural consequence of
not special-casing how the width was spelled. Both retired assertions were
replaced with `%x` (still genuinely unsupported, no real consumer) and
`%'d`/`%'s` (the comma flag paired with anything but `%u`), preserving the
same boundary-testing intent rather than just deleting coverage.

## The wide-character subsystem and `strvis`

`util.c`'s DEFAULT (non-`-b`/`-B`) escaping path, `printescaped()`, uses
`mbrtowc`/`wcrtomb`/`iswprint`/`wcwidth` -- NOT `strvis`, which is only
`safe_print()`'s (`-b`/`-B`) path. Since `isatty()` always reports true in
this runtime, `f_nonprint` defaults to 1, making the wide-character path
load-bearing for the DEFAULT invocation, not a corner case gated behind an
explicit flag. Implemented both:

- A real, honest single-byte-per-character C-locale wide-character
  subsystem (`cb_libc_mbrtowc`/`wcrtomb`/`iswprint`/`wcwidth` in
  `libc/cb_libc.c`, `libc/include/wchar.h`/`wctype.h`) -- the same
  commitment `LOCALE-01` already made (no locale database, no real
  multibyte encoding), applied to wide characters: genuinely stateless
  (`mbstate_t` carries no real state to track), not a fabricated decoder.
- Real `strvis` (`libc/include/vis.h`) for `-b`/`-B`, since it wasn't
  materially more work once the byte-escaping logic existed.

`wchar_t` itself is not redefined anywhere in this project -- `<stddef.h>`
(transitively included via `cannedbsd/abi.h`) already provides the host
compiler's own builtin `wchar_t`, the same fundamental-type exemption
`inttypes.h` already applies to `intmax_t`. `cannedbsd/libc.h`'s own
internal declarations of `cb_libc_mbrtowc`/`wcrtomb`/`wcwidth` spell their
wide-character parameters as `wchar_t` directly (visible there via the same
`<stddef.h>` chain) rather than erasing to `int` -- an early attempt to
erase to `int` produced a real conflicting-types error against
`libc/include/wchar.h`'s own declaration on this project's own Alpine/musl
target, where `wchar_t` is `unsigned int`, not `int`. `mbstate_t` (this
project's own opaque struct, not a compiler builtin) is spelled `void *` in
both places instead, for the same identical-declaration reason.

## `time(3)`/`ctime(3)`: a new ABI append

`print.c`'s `printtime()` needs `time(NULL)` (the CURRENT time, for its
six-month-cutoff date-vs-time-of-day decision) and `ctime()` (a file's
stored time, formatted). Neither existed as a task-facing capability:
`cb_api_v1` had no wall-clock accessor at all, only the kernel-internal
`struct cb_host_ops_v1.wall_clock_millis` did (already used internally by
`FS-STAT-01`'s own file timestamps).

- Appended `wall_clock_millis` to `cb_api_v1` (`CB_API_V1_WALL_CLOCK_MIN_SIZE`
  guard, same `offsetof`/`sizeof` pattern as every other optional append in
  `abi.h`), wired in `src/core.c` as `api_wall_clock_millis()` -- exposing
  the SAME already-real host capability to ordinary tasks, not a new one.
- `cb_libc_time()`: struct_size-guarded read of that field, real seconds
  since epoch.
- `cb_libc_ctime()`: a real civil-calendar epoch-to-date breakdown (Howard
  Hinnant's public-domain `civil_from_days` algorithm, correct across the
  full range a `uint32_t time_t` can represent, chosen over a naive
  year-counting loop), formatted into the exact fixed 26-byte
  `"Www Mmm dd hh:mm:ss yyyy\n\0"` layout `printtime()` reads via specific
  substring indices (`[4..10]`, `[11..15]` or `[11..23]`, `[20..23]`).
- Private `libc/include/time.h` (guards `time_t` with the same
  `_TIME_T_DECLARED` macro `compat/netbsd/include/sys/types.h` already
  uses, so both can be included together) intercepts the system's real
  `<time.h>` (`time_t`/`struct timespec` conflicts otherwise); a minimal
  `libc/include/tzfile.h` provides only the two constants (`DAYSPERNYEAR`,
  `SECSPERDAY`) `printtime()`'s `SIXMONTHS` macro actually uses, not the
  real header's on-disk TZif format/leap-second tables.

## The mode column and uid/gid: real values, not fabricated ones

`-l`'s permission string comes from `strmode(3)` applied directly to
`sp->st_mode` -- and `st_mode`'s low 12 bits are RAMFS's own real per-node
mode, tracked since node creation from whatever the creating `open()`/
`mkdir()` call passed (`node->mode` in `src/ramfs.c`, pre-existing since
before this session). This needed no new decision: it was already an
honest, real, already-committed value, not something this ID had to invent
-- permission ENFORCEMENT itself remains deferred for this milestone (no
access control is applied anywhere), exactly like every other command.
`uid`/`gid` are 0 for the same already-committed reason `FS-STAT-01`
documented: this runtime's single fixed answer for "the current user,"
reused, not a fabricated per-file value.

## Options: supported vs. honestly-failing

Supported (measured by running them, not assumed): default sorted listing,
`-1`, `-a`/`-A`, `-f` (also exercises `FTS_SEEDOT`), `-r`, `-t`/`-c`/`-u`
(real `FS-STAT-01` timestamps to sort on, for the first time), `-S`, `-i`,
`-n`, `-l` (mode/nlink/uid/gid/size/date columns, all real), `-R`, `-F`,
`-M` (real comma-grouped sizes), multiple directory operands with
per-directory headers.

Honestly failing (outside the accepted matrix, loud and specific, not
silently wrong): `-h`/`humanize_number` (`ENOSYS`) and anything reaching
`ioctl(TIOCGWINSZ)` (`ENOTTY`) -- termcap and real terminal-width detection
stay out of scope; the fixed 80-column fallback this runtime already uses
elsewhere applies here too. Since `isatty()` always reports true, `ls`'s
default column-layout and wide-character-escaping code paths are exercised
by every plain invocation, not just explicit `-C`/`-b` corner cases.

## Found, not fixed: pinned commands' file-scope statics never reset across invocations

`test_mv_behavior.sh`'s own multi-file-move case originally chained two
separate `ls` invocations in one script (`ls /home/user; ls /tmp`) and got
a stray blank line + `"/tmp:"` header on the SECOND, single-operand,
empty-directory call -- which alone prints nothing (verified). Traced to
`ls.c:410`'s `static int output;` ("if anything output"), set to 1 at
lines 468/673 whenever an earlier call had more than one real directory
operand, and never reset. Real BSD assumes a fresh, zeroed process image
per invocation; this runtime does not give pinned commands one --
`native_entry()` (`src/executor.c`) calls a program's `start()` directly
inside a cooperative-scheduler stack-switch, and `cb_libc_start()`
(`libc/cb_libc.c`) does nothing but rebind `bound_api` and call `main()` --
no `.bss`/`.data` segment is ever re-zeroed between invocations. Every
command's file-scope statics live in the one host process's memory for
that process's entire lifetime, so two `ls` calls in one script do not
behave like two independent processes the way `ls.c` itself assumes.

This is not new to `ls`: `notes/iterations/TEE-STATE-01-design.md` already
documents the identical hazard for `tee.c`'s global `head` pointer ("tasks
multiplex inside a single host process, so the global would leak... if
left unmanaged") and fixed it with a bespoke per-task global-swap wrapper
-- but that fix was never generalized into a documented runtime invariant,
and was never applied here. `cat.c`'s getopt-set flags (`bflag`/`eflag`/
`fflag`/`nflag`/etc., never reset at the top of `main`) and `mv.c`/`rm.c`'s
equivalent flag statics have the exact same latent bug, dormant only
because no existing test happens to chain a flagged invocation before a
flagless one of the same command in one script.

**Deliberately not fixed here**: `ls.c` is pinned, byte-for-byte; the
runtime-level fix (resetting each command's own statics per invocation, or
generalizing `TEE-STATE-01`'s per-task swap) is a cross-cutting decision
affecting every already-landed pinned command, not something this ID's
scope covers. Worked around, in-scope, by not writing a test that chains
two `ls` invocations in one script: `test_mv_behavior.sh`'s case now uses
a single `ls /home/user /tmp` call (real multi-operand headers) instead.
Flagged for the coordinator to decide the general fix, same as `STDIN-01`'s
`fclose` policy and `VFS-03`'s cursor were flagged rather than fixed
unilaterally.

**A second, more severe instance of the same root cause, found by the
sanitizer gate, not by inspection:** `print.c`'s `printcol()` (the DEFAULT
column layout `printfcn`, reached whenever a directory listing has more
than one entry and is not `-1`/`-x`/`-l`/`-m`) caches its random-access
array across calls in `static FTSENT **array` / `static int lastentries`,
by design -- real BSD `ls` never runs a second time in the same process,
so it never reallocates once `dp->entries <= lastentries`. This runtime's
task model makes that assumption false in a way that is not just
cosmetically wrong (like `output` above) but a genuine heap-use-after-free:
`src/core.c`'s `task_release_allocations()` frees every allocation a task
ever made when that task exits (the exact mechanism
`TEE-STATE-01-design.md` already documents for this same reason), so once
one `ls` task exits, its `array` allocation is gone -- and a second `ls`
task in the same host process, sharing `print.c`'s static, skips
reallocating (if its own `dp->entries` does not exceed the first task's)
and writes through the dangling pointer. Caught by the `sanitize` build,
not a passing normal build: `tests/test_core.c`'s own pre-existing
`lsinterleave` test (predating this ID, written to prove cooperative
task interleaving does not corrupt VFS traversal, using the old
non-caching `LS-01` stand-in) spawns two real `ls` tasks against
two-entry directories, interleaved via a deliberately-yielding `readdir`
-- exactly the shape that trips this. Fixed in-scope by passing `-1` to
both of that test's `ls` invocations (`printscol`, a plain linked-list
walk with no such cache) rather than the default column mode -- the test's
own purpose (VFS traversal interleaving safety) does not depend on which
column mode renders the result, so this preserves the test's real intent
without touching pinned source or inventing a `TEE-STATE-01`-scale fix
unilaterally. **This is a real, currently-shippable landmine beyond this
one test**: any real usage sequence that runs the default (non-`-1`)
column `ls` twice in one process without the entry count strictly growing
will hit the same use-after-free. Flagged for the coordinator alongside
the `output` finding above -- both point at the same missing runtime
capability (per-invocation state isolation for pinned commands' file-scope
statics), which `cat.c`'s own unreset getopt flags and `mv.c`/`rm.c`'s
equivalents already share latently (confirmed by inspection, not yet
triggered by any existing test).
