## Change and review

**Implementation** (`commands/ls.c`, `commands/ls_module.c`): cannedBSD-owned,
not an unchanged upstream import -- no `UPSTREAM.md` entry applies, matching
the entry's own scope note. Enumerates one directory operand (default `.`)
over `opendir`/`readdir`/`closedir`, one name per line via `puts`. Does not
sort -- RAMFS's own child order (prepend-ordered, most-recently-created
first) is what "stable deterministic ordering" means here, and the shell
test proves it's the *same* order across two back-to-back listings, not
just that some order exists once.

A named operand that exists but is not a directory (a plain file, or -- as
tested -- an executable command node under `/bin`) is printed by name
instead of erroring, matching real `ls`'s file-operand behavior. This is
done **without calling `stat()`**, because no public `struct stat` exists
yet (`libc/include/sys/stat.h` is presently a two-line stub -- see
`FILEUTIL-01`'s `cat` findings). Instead it distinguishes the three cases
using `opendir`'s own existing `ENOTDIR` vs. other-error result, which
`VFS-03`'s `cb_vfs_opendir_path` already provides for free. Deliberately not
implemented: sorting, `-l`, multi-column width, termcap, `getpwuid`/
`getgrgid`, `fts`, dotfile filtering (RAMFS's dirent contract has no
synthetic `.`/`..` entries to filter in the first place), and multi-operand
argv handling (two or more operands are rejected with a usage diagnostic,
matching this project's existing house style for other bounded commands
rather than silently ignored or crashed on).

**ABI, ownership, and cleanup review:**
- `commands/ls.c` calls `closedir()` on every exit path (successful
  enumeration, a `puts` failure mid-listing, and a genuine `readdir` error
  distinguished from clean EOF by clearing `errno` immediately before each
  call and checking it after the loop breaks -- the exact convention
  `src/core.c`'s `api_readdir` itself documents: "touching \[errno\] here
  \[on clean EOF\] would defeat" the caller's own ability to tell EOF from
  error). Verified under the ASan `sanitize` build across all
  `test_ls_behavior.sh` cases with no leak reported.
- `src/internal.h`'s `CB_MAX_PROGRAMS` raised from 64 to 72. Not a
  versioned-ABI change (it bounds an internal `struct cb_kernel` array, not
  any `cb_api_v1`/`cb_program_v1`/`cb_stat_v1` field) -- but real and
  necessary: `cb_register_base_programs()` plus the test suite's own
  `FIXTURE_FULL` registrations totaled exactly 65 once `ls` became a base
  program, one over the previous ceiling. Comment at the definition records
  the measured count that drove the new value; not a speculative allowance.
- The new `lsinterleave` C-level test (`tests/test_core.c`) proves
  independent cursors under forced interleaving: a per-task-overridden
  `api.readdir` (mirroring the existing `err_interleave`/`truncateinterleave`
  technique already in this file) yields after every call, two `ls`
  invocations against two different, disjoint directories are spawned
  concurrently, `ls_switches >= 2` proves the scheduler actually alternated
  between them rather than running one to completion first, and the merged
  captured stdout is checked (order-independently, like the existing
  `err_interleave` check) for all four expected names from both directories
  with none lost, duplicated, or misattributed. Registered under a new
  `FIXTURE_LS` (value 9) rather than folded into `FIXTURE_FULL`, following
  the exact precedent `FIXTURE_DIRENT` already set for the same 64-slot
  ceiling reason (see the `CB_MAX_PROGRAMS` bump above).
- No host process, filesystem, thread, signal, socket, or terminal call was
  added to the portable core; `ls.c` uses only the existing libc veneer
  (`dirent.h`, `errno.h`, `err.h`, `stdio.h`).
