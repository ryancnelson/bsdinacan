# PORT32-01: 32-bit resource boundary audit for unchanged head

Documentation-only audit, based on `origin/main` (merged to `731b447`
for this revision; originally started at `4ef9f83`). No runtime change,
no invented API, no capture-buffer growth, and no guest control is
claimed or proposed here. This traces the actual task-stack allocation
path on Linux and Mac, the pinned `head.c`'s own 65536-byte automatic
buffer, RAMFS's file-size and peak-memory behavior during growth, and
the descriptor redirection APIs needed to validate
`notes/iterations/HEAD-01-testplan.md` case 14 (a 65538-byte result),
per `BACKLOG.md`'s `PORT32-01` scope (read from commit `88ac973`).

**Revision note**: an earlier version of this audit contained several
errors independent review caught before merge -- a wrong optimization
flag (measured with `-O2`, the real Mac build uses `-Os`), a Linux
toolchain that does not match the actual pinned CI environment, an
overstated Mac stack reservation, an unproven "zero overhead" claim on
Linux, an incorrect description of which side of a spawn a
`CB_SPAWN_CLOSE` action closes, a false claim that already-landed
`getopt`/`getc`/`putchar`/`err`/`errx`/`warn`/`fread` veneers "do not
exist yet," an incomplete RAMFS peak-memory analysis, and a wrong
conclusion that the Mac guest acceptance harness cannot exercise case
14 at all. Each is corrected below, in place, with the real measured
numbers this time -- not left as a separate erratum.

## Stack allocation: two platforms, corrected arithmetic on both

`struct cb_program_v1.requested_stack_size` (`include/cannedbsd/abi.h:236`)
is a plain `size_t`; `0` means "use the default." Both platforms'
executor layer resolve it identically:

```c
// src/executor.c:179-183
size_t stack_size = program->descriptor.requested_stack_size;
...
if (stack_size == 0)
    stack_size = 64 * 1024;
native->context = task->kernel->host->context_create(
    native_entry, native, stack_size);
```

`context_create` is host-specific, and this audit's first draft
overstated the difference between the two hosts' own bootstrap cost.

**Linux** (`src/host_linux.c:56-80`): `context->stack = malloc(stack_size);`,
used directly as the `ucontext` stack. This project's *own* code
reserves nothing. But `makecontext`/`swapcontext` themselves are C
library functions with their own bootstrap cost this project's source
does not control -- **the first draft's claim that this made Linux
"zero overhead" was wrong, and is retracted here**, not just softened.
Measured directly (not assumed): a small program that fills a 262144-byte
stack buffer entirely with a `0xAA` sentinel, calls `getcontext`/
`makecontext`, `swapcontext`s into that context and immediately back
without running any task code, then scans from the top of the buffer
for the highest touched byte -- compiled and run inside the exact
pinned CI agent image (`tribblix-woodpecker-agent:3.18.0`, Alpine
3.22.5, linking `-lucontext` exactly as `.woodpecker/ci.yml` does)
-- shows **9 bytes** touched from the top before any task code runs.
Genuinely small, but genuinely nonzero; the correct claim is "measured
at 9 bytes on this exact library," not "zero by construction."

**Mac** (`platform/mac68k/host_mac.c:185-203`): allocates `stack_size +
4` bytes (4-byte alignment padding, not usable frame space); rejects
`stack_size < 1024` or `> INT32_MAX - 4`. `context_create` places the
initial machine-context frame at `frame = align4(stack + stack_size) -
14 words` (`56` bytes) and fills it via `cb_mac_context_seed`
(`platform/mac68k/context.S:20-24`, saving `%d2-%d7/%a2-%a6` = 11
registers = 44 bytes) plus three more words: `frame[11]` = the real
entry point, `frame[12] = 0` ("must not return"), `frame[13]` = the C
argument.

**The first draft claimed all 56 of those bytes come out of the
requested budget permanently. This is wrong, and is corrected here by
actually tracing `cb_mac_context_swap`** (`platform/mac68k/context.S:5-17`),
not just citing the allocation site:

```
move.l (%a1),%sp                 ; SP = frame  (context->saved_sp)
movem.l (%sp)+,%d2-%d7/%a2-%a6    ; pops 11 regs = 44 bytes; SP = frame+44
move.l 4(%a1),0x0110
rts                                ; pops frame[11] as the target PC,
                                    ; jumps to context_entry; SP = frame+48
```

By the time `context_entry` (`host_mac.c:159-162`, itself a two-line
function that calls `context->entry(context->argument)`) starts
running, `SP = frame + 48 = (stack top - 56) + 48 = stack top - 8`.
**Only 8 bytes of the original 56-byte frame remain permanently
consumed** (`frame[12]`/`frame[13]`, left below the new SP as
already-delivered call-argument residue); the other 48 bytes were
reclaimed by the `movem`/`rts` sequence and are ordinary, reusable stack
space once more. `context_entry`'s own small prologue (calling
`context->entry`, which is `native_entry`) adds a further few bytes on
top of that 8 -- folded into "live call frames" below, not itemized
separately, since it is architecturally the same kind of cost as any
other call in the chain.

Neither host detects stack overflow at runtime; this audit does not
propose adding detection.

## Measured: the pinned source's own stack frames, on the actual pinned toolchains

The first draft measured Mac with `-O2` (the real
`platform/mac68k/CMakeLists.txt` uses `-Os`) and Linux with this
worktree host's own system `gcc` 13.3.0 (not the pinned CI agent's
Alpine 3.22.5 / GCC 14.2.0). Both are corrected here, re-measured
against the actual flags and the actual pinned toolchain, over the same
SSH/Docker access to the CI runner host the reviewed `CONV-01-design`
Retro68 measurement already established. Full exact commands and shim
contents are retained below so this is independently reproducible, per
review.

Every declaration these single-file, unlinked stack-frame measurements
need but that this project's own private headers don't yet supply
(`getopt`/`optarg`/`optind` on the Mac side specifically -- the Linux
side already has real declarations at this base, but the isolated
single-TU compile still needs a prototype for `getprogname`, which this
project declares as a *macro* to `cb_libc_getprogname`, not a
plain-named symbol the pinned source's own unmodified `getprogname()`
call can resolve against in an isolated, unlinked compile) was supplied
via a minimal `-include` shim -- prototypes only, never a definition,
never linked, and not proposed as part of any header this project
ships:

**Mac** (`m68k-apple-macos-gcc` 16.1.0, exact pinned image
`ghcr.io/autc04/retro68@sha256:459dd3ea9856262162615527021be7b64f198631dc59cca8cedbf197b7656019`,
flags matching `platform/mac68k/CMakeLists.txt` exactly):

```
$ cat shim.h

$ m68k-apple-macos-gcc -std=c99 -Os -ffunction-sections -fdata-sections \
    -Wall -Wextra -fstack-usage -include shim.h -c head.c -o head.o

head.c:71:1:main     80       dynamic,bounded
```

**Linux** (`cc` inside `tribblix-woodpecker-agent:3.18.0`, confirmed by
running it directly: `Alpine gcc (Alpine 14.2.0) 14.2.0`, matching
`.woodpecker/ci.yml`'s `image: bash` step, which this project's own
"local backend" agent -- baked into that same image -- actually
executes inside, not this design-worktree host's own separate system
compiler):

```
$ cat shim.h
const char *getprogname(void);
$ cat sys/cdefs.h
#define __COPYRIGHT(x)
#define __RCSID(x)
#define __dead __attribute__((noreturn))

$ cc -std=c99 -D_XOPEN_SOURCE=700 -O2 -fstack-usage \
    -I. -include shim.h -c head.c -o head.o
head.c:143:1:head.part.0    65600    static
head.c:143:1:head           32       static
head.c:71:1:main             96       static
```

GCC 14.2.0 split `head` into a tiny 32-byte stub and an outlined
`head.part.0` (65600 bytes) that the stub calls into and that remains
on the stack, alongside the stub's own 32 bytes, for the duration of
the actual buffer-filling work -- both frames are simultaneously live,
not alternatives.

**Corrected concurrent totals**, `main` + `head` (+ `head.part.0` on
Linux) simultaneously live:

- Mac: `80 + 65584` = **65664 bytes**.
- Linux: `96 + 32 + 65600` = **65728 bytes**.

Both, independent of the correction, still exceed the existing 64 KiB
(65536-byte) default `src/executor.c` falls back to -- the plan's own
"Red" concern (`HEAD-01-testplan.md`) holds under the corrected,
CI-matching numbers too.

## RAMFS: no fixed ceiling below the host allocator's own, corrected peak-memory arithmetic for this exact case

`src/ramfs.c`'s growth path (`api_write`'s callers, lines `418-458`)
doubles capacity with no ceiling of its own below `SIZE_MAX`:

```c
// src/ramfs.c:441-450
if (needed > node->capacity) {
    capacity = node->capacity == 0 ? 64 : node->capacity;
    while (capacity < needed) {
        if (capacity > SIZE_MAX / 2) { capacity = needed; break; }
        capacity *= 2;
    }
    new_data = cb_resize(task->kernel, node->data, capacity);
    ...
}
```

**The first draft stopped there. It should not have**: the actual host
allocator this eventually reaches on Mac has its own real ceiling and
its own real peak-memory behavior during growth, both read directly
from `platform/mac68k/host_mac.c`, not assumed:

```c
// host_mac.c:109-114 -- host_allocate rejects size > INT32_MAX
static void *host_allocate(size_t size)
{
    struct memory_call call = {NULL, size, NULL};
    if (size > INT32_MAX) return NULL;
    ...
}

// host_mac.c:127-140 -- host_resize allocates the NEW buffer, copies
// the OLD data into it, THEN releases the OLD buffer: both are live
// simultaneously during the copy, and it too rejects size > INT32_MAX.
static void resize_on_root(void *argument)
{
    ...
    call->result = host_allocate(call->size);
    if (call->result == NULL) return;
    old_size = GetPtrSize((Ptr)call->pointer);
    memcpy(call->result, call->pointer, ...);
    host_release(call->pointer);
}
```

For a 65538-byte file, `src/ramfs.c`'s doubling sequence is `64, 128,
256, ..., 65536, 131072` -- `65536 < 65538`, so it grows one step past
that to **131072 bytes final capacity**, for *each* of the input and
output files this audit's proposed fixture needs. The proposed
fixture's own bounded-write population strategy for the *input* file
completes (and its own transient old+new doubling peaks resolve) before
the *output* file's growth begins, so the two files' growth peaks are
not simultaneous with each other -- except at the single moment the
*output* file's own last doubling step (`65536 -> 131072`) is itself in
progress, while the input file already sits at its own settled
131072-byte capacity: **131072 (input, settled) + 65536 (output, old
buffer, not yet released) + 131072 (output, new buffer, mid-copy) =
327680 bytes**, before any struct/VFS-node metadata or task stacks. This
is a real, bounded, computable number this audit did not previously
account for -- not a proposal to change RAMFS's own growth algorithm or
raise any ceiling (no runtime expansion is requested here); the
implementing task's own fixture must check `host_allocate`/
`host_resize`'s (and, by extension, `cb_resize`'s) return values for
allocation failure explicitly and treat it as a real, handled test
outcome, and the coordinator's own guest run is the place to confirm
327680 bytes plus the rest of a booted System 7 environment's own
footprint actually fits in whatever heap size the Basilisk II guest is
actually configured with -- a genuinely pending measurement, not
claimed here.

## Descriptor redirection: existing APIs are sufficient -- corrected description of which side `CB_SPAWN_CLOSE` closes

`struct cb_spawn_action_v1`/`CB_SPAWN_DUP2`/`CB_SPAWN_CLOSE`
(`include/cannedbsd/abi.h:74-84`) and `api->stat`/`struct cb_stat_v1`
(with a `uint64_t size` field, `abi.h:65-72`) are already declared and
already exercised by a directly analogous existing test.

**The first draft's description of this test's own mechanics was
wrong, and is corrected here**: `CB_SPAWN_CLOSE`/`CB_SPAWN_DUP2` actions
are applied to the *child's own* descriptor table during its spawn
setup (`src/core.c:571-586`, operating on `task->descriptors[...]` for
the task being created) -- they do not touch the parent's descriptors
at all. The *parent* must separately, explicitly call `api->close()` on
its own copies of any descriptor it handed to the child, after
`api->spawn` returns, exactly as the existing precedent already does:

```c
// tests/test_core.c:3090-3106 (stdioepipeprobe_main)
if (api->pipe(descriptors) < 0) return 234;
if (api->close(descriptors[0]) < 0) return 235;   // parent's own close,
                                                    // before spawn
...
actions[0].type = CB_SPAWN_DUP2;   // duplicates into the CHILD
actions[0].from_fd = descriptors[1];
actions[0].to_fd = 1;
actions[1].type = CB_SPAWN_CLOSE;  // closes in the CHILD, not here
actions[1].from_fd = descriptors[0];
...
if (api->spawn("stdioprobe", child_argv, envp, actions, 3, &child) < 0)
    return 236;
if (api->close(descriptors[1]) < 0) return 237;   // parent's own close,
                                                    // after spawn
```

This audit's proposed fixture reuses this exact pattern with an opened
RAMFS file descriptor (from `api->open`'s existing
`CB_O_WRONLY | CB_O_CREAT | CB_O_TRUNC` flags, already used elsewhere,
e.g. `tests/test_core.c:1852`) in place of a pipe's write end.

## Proposed concrete fixture -- corrected: one portable probe, both platforms

**The first draft's central conclusion was wrong, and is retracted
here, not merely softened**: it claimed the Mac guest acceptance
harness's small, fixed captured-output comparison
(`platform/mac68k/acceptance_cases.def` + `guest.py`, backed by
`static char captured[4096];`, `host_mac.c:34`) made case 14
unreachable on Mac without growing that buffer. **This conflated two
different things**: the *harness's own string-matching mechanism* (genuinely
limited to whatever short string a registered program prints) with
*what a registered program is actually allowed to do internally* before
printing that short string. Every existing probe in this project
(`libcbasenameprobe`, `libcstrtoimaxprobe`, etc.) already does exactly
this: substantial internal verification, then a compact `""` or short
result on success. A `head`-exercising probe that internally spawns
`head` with its stdout redirected to a RAMFS file, `api->stat`s it, and
`api->read`s it back in bounded chunks -- exactly the pattern
`HEAD-01-testplan.md` already calls for in its own note on case 14 --
prints nothing large itself; it only prints a short pass/fail
indicator, which fits the existing 4096-byte Mac capture exactly as
well as any other registered probe already does. **The original test
plan's own requirement (bounded-chunk verification with a compact
result, on both platforms) does not need replacing with a smaller
substitute or a mere crash-observation fallback; it needs one portable,
already-declared-API-only registered program**, buildable and
registerable on both `src/programs.c`/`tests/test_core.c` (Linux
native, its own new scoped fixture, mirroring `FIXTURE_CONV`/
`FIXTURE_YES`) and `platform/mac68k/CMakeLists.txt`/`main.c`/
`acceptance_cases.def` (Mac guest, exactly like every other probe
already listed there) simultaneously. Not implemented here -- this is
the smallest concrete shape the implementing `HEAD-01` task should
build:

1. Pre-populate an input RAMFS file (e.g. `/tmp/head-input`) with
   exactly 65538 `'A'` bytes, written in bounded chunks from a small
   local buffer (mirroring `ramfsprobe_main`'s own existing
   file-population style) -- never holding all 65538 bytes in one
   in-memory array. Check every `api->write`'s return value; a real
   allocation failure from the RAMFS growth path above is a genuine,
   handled test outcome, not assumed away.
2. `api->open` that file read-only; `api->open` a second, output RAMFS
   file (`/tmp/head-output`) write-only/create/truncate. Check both
   for a valid (non-negative) descriptor.
3. `cb_spawn_action_v1[4]`: `DUP2(input_fd, 0)`, `DUP2(output_fd, 1)`,
   `CLOSE(input_fd)`, `CLOSE(output_fd)` -- these two `CLOSE` entries
   apply to the *child's* inherited copies, per the correction above;
   the *parent* separately calls `api->close()` on its own `input_fd`/
   `output_fd` after `api->spawn` returns, exactly like
   `stdioepipeprobe_main` does for its pipe descriptors.
4. `api->spawn("head", {"head", "-c", "65538", NULL}, ...)`,
   `api->waitpid`, assert exit status `0`.
5. `api->stat("/tmp/head-output", &st)`; assert `st.size == 65538`
   *before* reading anything -- proving the exact byte count without
   holding the content.
6. `api->open` the output file again read-only; `api->read` it in
   bounded chunks (e.g. 4096 bytes at a time) into a small stack
   buffer, asserting every byte is `'A'` and the chunk lengths sum to
   exactly 65538. Never allocate or compare a 65538-byte buffer in one
   piece.
7. Print a short, fixed result (`""` on success, matching every other
   probe's own convention) and return `0` -- this is the only output
   either harness ever needs to match against, on either platform.
8. Register it under its own new, minimal scoped fixture on Linux
   (mirroring `FIXTURE_CONV`/`FIXTURE_YES`, not `FIXTURE_FULL`, which
   prior iterations already found sits at or near `CB_MAX_PROGRAMS`'s
   ceiling), and add the matching entries to
   `platform/mac68k/CMakeLists.txt`, `main.c`'s checked registration
   chain, and one new `acceptance_cases.def` line, exactly like every
   prior probe addition this session has already done for other
   backlog items.

This is the same one fixture design on both platforms, using only
already-declared APIs, matching `HEAD-01-testplan.md`'s own case-14
requirement exactly rather than substituting a smaller case set or a
mere "did it crash" observation. Actually building, registering,
compiling, and running it -- on both platforms, including the
coordinator's own guest run -- remains genuinely pending, not claimed
here.

## Scope discipline

audit. No new API is declared or proposed as implemented. No capture
buffer is resized. No RAMFS growth algorithm or ceiling is changed --
its existing, real behavior is only described more completely than the
first draft did. `HEAD-01`'s own implementation, its actual fixture
code, and all guest acceptance remain separate, not-yet-started work,
