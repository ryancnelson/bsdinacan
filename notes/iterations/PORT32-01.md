# PORT32-01: 32-bit resource boundary audit for unchanged head

Documentation-only audit, based on fresh `origin/main` (`4ef9f83`). No
runtime change, no invented API, no capture-buffer growth, and no guest
control is claimed or proposed here. This traces the actual task-stack
allocation path on Linux and Mac, the pinned `head.c`'s own 65536-byte
automatic buffer, RAMFS's file-size behavior, and the descriptor
redirection APIs needed to validate `notes/iterations/HEAD-01-testplan.md`
case 14 (a 65538-byte result), per `BACKLOG.md`'s `PORT32-01` scope (read
from commit `88ac973`).

## Stack allocation: two different platforms, two different arithmetics

`struct cb_program_v1.requested_stack_size` (`include/cannedbsd/abi.h:236`)
is a plain `size_t` field; `0` is a sentinel meaning "use the default."
Both platforms' executor layer resolve it identically:

```c
// src/executor.c:179-183
size_t stack_size = program->descriptor.requested_stack_size;
...
if (stack_size == 0)
    stack_size = 64 * 1024;
native->context = task->kernel->host->context_create(
    native_entry, native, stack_size);
```

`context_create` is a host-specific callback, and the two hosts do
genuinely different things with the same `stack_size` value:

- **Linux** (`src/host_linux.c:56-80`): `context->stack = malloc(stack_size);`
  -- a plain heap buffer, used directly and entirely as the `ucontext`
  stack (`uc_stack.ss_sp`/`ss_size` set to that exact pointer/size). No
  bytes are reserved for the runtime's own bookkeeping; the full
  `requested_stack_size` is available to the task's own call chain.
- **Mac** (`platform/mac68k/host_mac.c:185-203`): rejects `stack_size <
  1024` or `> INT32_MAX - 4`; allocates `stack_size + 4` bytes (the extra
  4 bytes are for 4-byte alignment of the frame pointer, not usable call
  frame space); then places the initial machine-context frame `frame -=
  14` 32-bit words (`= 56 bytes`) below the top of that buffer, before
  any task code runs, to hold "11 saved registers, entry PC, return PC,
  and the C argument" (the code's own comment, `host_mac.c:200`). **This
  56 bytes comes out of the requested budget before the task's own call
  chain gets to use any of it** -- a genuine, measured difference from
  Linux's plain `malloc`, not a symmetrical assumption. There is no
  stack-overflow guard on either platform: a genuine overflow on Mac
  corrupts whatever `host_allocate` handed back next; on Linux it
  corrupts whatever `malloc` returned adjacent to it. Neither host
  detects this at runtime today, and this audit does not propose adding
  detection (that would be a runtime change, out of scope here).

## Measured (not estimated): the pinned source's own stack frames

`head.c`'s automatic buffer is exactly what the test plan already cites:

```c
// head.c:145 (pinned revision b890038f7ae5831ab0b6eda87cb0a2d4aee00c2c)
char buf[65536];
```

Rather than hand-estimate the surrounding frame overhead, this audit
actually compiled the unmodified pinned source with `-fstack-usage`
(a real GCC flag emitting each function's own measured frame size) on
**both** the exact toolchains this project's own CI uses, reachable over
SSH on the CI runner host exactly as the reviewed `CONV-01-design`
Retro68 measurement did. Minimal, empty/trivial declarations were
supplied via `-include` only for the handful of symbols this
isolated single-file compile needs that aren't yet declared anywhere in
this project's own private headers (`getopt`/`optarg`/`optind`,
`getprogname`, `__dead`/`__COPYRIGHT`/`__RCSID`) -- these are
prototype-only shims to make an **unlinked, single-file stack-frame
measurement** of the exact pinned bytes possible; they are not proposed
as part of any header this project ships, and nothing here is linked,
run, or claimed as a working `head` build.

**Mac** (`m68k-apple-macos-gcc`, GCC `16.1.0`, the exact pinned Retro68
image `ghcr.io/autc04/retro68@sha256:459dd3ea9856262162615527021be7b64f198631dc59cca8cedbf197b7656019`):

```
$ m68k-apple-macos-gcc -std=c99 -O2 -fstack-usage -c head.c -o head.o
head.c:143:1:head    65588    dynamic,bounded
head.c:71:1:main     92       dynamic,bounded
```

**Linux** (`gcc` 13.3.0, the same CI runner host Woodpecker's own local
backend executes on):

```
$ gcc -std=c99 -D_XOPEN_SOURCE=700 -O2 -fstack-usage -c head.c -o head.o
head.c:143:1:head    65600    static
head.c:71:1:main     96       static
```

`head()`'s measured frame (65588/65600 bytes) already includes the
65536-byte `buf` plus its own locals (`size_t len, rv, rv2; int ch;`) and
whatever the compiler's own frame/alignment overhead is; `main()`'s
measured frame (92/96 bytes) includes its own locals, notably two
`intmax_t` (8-byte, even on Mac's ILP32 target, per `CONV-01`) counters.
Since `main` calls `head`, both frames are simultaneously live on the
stack for the entire duration of `head()`'s execution: **the real,
measured minimum concurrent stack depth is 65680 bytes on Mac and 65696
bytes on Linux** -- not an estimate.

**This alone already exceeds the existing 64 KiB (65536-byte) default**
that `src/executor.c` falls back to when `requested_stack_size` is left
at `0`, on *both* platforms, independent of any further library call
overhead. This is exactly the plan's own stated "Red" concern
(`HEAD-01-testplan.md`: "Existing default 64 KiB stack cannot be assumed
sufficient"), now backed by a real compiled measurement rather than
restated as an assumption.

## Pending (explicitly not measured here, and why)

The 65680/65696-byte figures above cover only `head()` and `main()`
themselves. While `buf` is live, `head()` also calls `fread`/`fwrite`/
`getc`/`putchar`/`err`/`errx`/`warn` (via whatever private veneer
eventually backs them) -- each of those callees' *own* stack frames are
additionally, if briefly, live on top of `head()`'s frame during the
call. Those veneers do not exist yet (`STDIN-01`/`FWRITE-01`/`ERR-02`
are separate, not-yet-fully-landed backlog items as of this audit's
base), so their real per-call frame sizes cannot be measured the same
way `head()`/`main()`'s were -- there is no real implementation to
compile yet. This is recorded as a genuinely pending measurement, not
guessed at as if it were known: the smallest defensible statement is
that ordinary, non-recursive C wrapper functions with a handful of local
variables and no large automatic buffers of their own typically consume
tens of bytes of frame each, not thousands, so a few hundred bytes of
margin is a reasonable expectation -- explicitly labeled as an
expectation, not a measured fact, and the actual implementing task
should re-measure with `-fstack-usage` on the real veneer
implementations once they exist, exactly as this audit did for `head()`
itself.

## Stack budget arithmetic

| Component | Mac (measured/estimated) | Linux (measured/estimated) |
| --- | --- | --- |
| `main()` + `head()` combined frames | 65680 bytes (measured) | 65696 bytes (measured) |
| Host context-switch reservation | 56 bytes (measured, `host_mac.c:200`) | 0 bytes (measured, plain `malloc`) |
| Library callee frames (`fread`/`fwrite`/`getc`/`putchar`/`err`/`errx`/`warn`) | not yet measurable; expected low hundreds of bytes | not yet measurable; expected low hundreds of bytes |
| **Running total (measured parts only)** | **65736 bytes** | **65696 bytes** |
| Plan's own proposed `requested_stack_size` | `96 * 1024` = `98304` bytes | `98304` bytes |
| **Headroom over measured parts** | **32568 bytes** | **32608 bytes** |

`96 * 1024` is not proven safe by this audit (that would require the
still-pending library-frame measurements plus an actual guest/native run
that exercises the full path without corruption), but it is now backed
by a concrete arithmetic argument with roughly 32 KiB of headroom over
the two functions that dominate the frame -- not merely "a number that
sounded plausible." A ~32 KiB margin comfortably covers even a
pessimistic few-hundred-byte-per-frame estimate for the still-unmeasured
library calls, several times over.

## RAMFS: no size ceiling found, growth is dynamic

`src/ramfs.c`'s file-growth path (`api_write`'s callers, lines
`418-458`) uses a doubling-capacity strategy with no fixed upper bound
other than `SIZE_MAX` itself:

```c
// src/ramfs.c:441-450
if (needed > node->capacity) {
    capacity = node->capacity == 0 ? 64 : node->capacity;
    while (capacity < needed) {
        if (capacity > SIZE_MAX / 2) {
            capacity = needed;
            break;
        }
        capacity *= 2;
    }
    new_data = cb_resize(task->kernel, node->data, capacity);
    ...
}
```

There is no RAMFS-specific ceiling smaller than available host memory
that would reject a 65538-byte file. This was confirmed by reading the
actual growth path directly, not assumed from the absence of an obvious
constant.

## Descriptor redirection: existing, already-proven APIs are sufficient

Nothing new is needed. `struct cb_spawn_action_v1`/`CB_SPAWN_DUP2`/
`CB_SPAWN_CLOSE` (`include/cannedbsd/abi.h:74-84`) and `api->stat`/
`struct cb_stat_v1` (with a `uint64_t size` field, `abi.h:65-72`) are
already declared and already exercised by an existing, directly
analogous test:

```c
// tests/test_core.c:3098-3106 (stdioepipeprobe_main), the exact
// redirect-a-descriptor-into-a-spawned-child pattern this design reuses
actions[0].type = CB_SPAWN_DUP2;
actions[0].from_fd = descriptors[1];
actions[0].to_fd = 1;
actions[1].type = CB_SPAWN_CLOSE;
...
if (api->spawn("stdioprobe", child_argv, envp, actions, 3, &child) < 0)
    return 236;
```

That existing case redirects a *pipe's* write end onto descriptor 1;
this audit's proposed fixture redirects an *opened RAMFS file's*
descriptor onto descriptor 1 instead -- the same `CB_SPAWN_DUP2` action,
a different kind of descriptor behind it, already supported by
`api->open`'s existing `CB_O_WRONLY | CB_O_CREAT | CB_O_TRUNC` flags
(already used elsewhere, e.g. `tests/test_core.c:1852`).

## Proposed concrete fixture (Linux-native; Mac's own gap is stated honestly below)

Not implemented here -- this is the smallest concrete shape the
implementing `HEAD-01` task should build, using only already-declared
APIs:

1. Pre-populate an input RAMFS file (e.g. `/tmp/head-input`) with
   exactly 65538 `'A'` bytes, written in bounded chunks from a small
   local buffer (mirroring `ramfsprobe_main`'s own existing
   file-population style) -- never holding all 65538 bytes in one
   in-memory array.
2. `api->open` that file read-only; `api->open` a second, output RAMFS
   file (`/tmp/head-output`) write-only/create/truncate.
3. `cb_spawn_action_v1[4]`: `DUP2(input_fd, 0)`, `DUP2(output_fd, 1)`,
   `CLOSE(input_fd)`, `CLOSE(output_fd)` (closing the parent's own
   copies post-dup, exactly like the existing `stdioepipeprobe_main`
   pattern already does for its pipe fds).
4. `api->spawn("head", {"head", "-c", "65538", NULL}, ...)`,
   `api->waitpid`, assert exit status `0`.
5. `api->stat("/tmp/head-output", &st)`; assert `st.size == 65538`
   *before* reading anything -- proving the exact byte count without
   needing to hold the content.
6. `api->open` the output file again read-only; `api->read` it in
   bounded chunks (e.g. 4096 bytes at a time, deliberately matching the
   Mac capture ceiling's own size for no reason other than familiarity)
   into a small stack buffer, asserting every byte read is `'A'` and
   that the chunk lengths sum to exactly 65538. Never allocate or
   compare a 65538-byte buffer in one piece.
7. Register this as its own new, minimal scoped fixture (mirroring
   `FIXTURE_CONV`/`FIXTURE_YES`'s own precedent) rather than adding to
   `FIXTURE_FULL`, which prior iterations have already found sits at or
   near `CB_MAX_PROGRAMS`'s ceiling.

This exercises the exact call chain (`main` → `head` → `fread`/`fwrite`)
this audit measured the frame sizes of, with a real spawned child using
the `requested_stack_size` the implementing task assigns to `head`'s own
`cb_program_v1` entry -- the actual falsifiable proof the stack budget
above is real, not just arithmetic.

### The honest Mac-side gap

`platform/mac68k`'s own acceptance mechanism
(`platform/mac68k/acceptance_cases.def` + `guest.py`'s
`expected_result()`) is fundamentally a small, fixed-size captured-output
comparison (`static char captured[4096];`, `platform/mac68k/host_mac.c:34`)
-- it cannot represent a 65538-byte expected string without growing that
buffer, which this audit's own scope explicitly forbids ("no capture
growth"). **This audit does not propose a way to run case 14's exact
65538-byte content check on the Mac guest within the existing
harness**, and says so plainly rather than inventing new Mac-side
capture infrastructure to paper over the gap. The achievable Mac-side
evidence for `head`'s stack safety is: (a) the measured `-fstack-usage`
numbers above, from the exact pinned Retro68 compiler; (b) the smaller
test-plan cases (1-13, 15-18) that fit within the existing 4096-byte Mac
capture, once `head` itself is actually imported; and (c) the
coordinator's own eventual guest run actually executing the `-c 65538`
case and observing whether the emulated Mac either produces correct
output or visibly corrupts/crashes -- a pending measurement this audit
cannot perform, not a claim this audit makes on the guest's behalf.

## Measured vs. pending, summarized

**Measured** (compiled and observed directly, this audit):
- `head()`/`main()`'s exact stack frame sizes on both the pinned Mac
  cross-compiler and a real Linux GCC, via `-fstack-usage`.
- Mac's `context_create` allocates `stack_size + 4` bytes and reserves
  56 bytes of it for its own initial frame before task code runs.
- Linux's `context_create` uses `malloc(stack_size)` with no reservation.
- RAMFS's growth path has no fixed ceiling below `SIZE_MAX`.
- The exact existing APIs (`CB_SPAWN_DUP2`, `api->stat`, `api->open`)
  already used by an existing, directly analogous test.

**Pending** (explicitly not measured or executed here):
- The real per-call stack frame sizes of `fread`/`fwrite`/`getc`/
  `putchar`/`err`/`errx`/`warn`'s eventual private veneers, which do not
  exist yet.
- Any actual compile, link, or run of the fixture proposed above.
- Any Mac guest run of any kind -- this remains the coordinator's own
  action, per this project's established acceptance-ownership rule.
- Whether `96 * 1024` is the final, correct `requested_stack_size` --
  this audit's arithmetic supports it as a reasonable, headroom-backed
  choice, not a proof.

## Scope discipline

No `platform/mac68k`, `src/`, or `tests/` file is modified by this
audit. No new API is declared or proposed as implemented. No capture
buffer is resized. `HEAD-01`'s own implementation, its actual fixture
code, and all guest acceptance remain separate, not-yet-started work.
