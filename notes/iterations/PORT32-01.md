`8b0b1cb53e5f7599c57539652477863617a3145e` (all three exact #314 workflows
passed). The statements below about unlanded fwrite, pending private builds,

peak-memory behavior, and the descriptor redirection APIs needed for
`notes/iterations/HEAD-01-testplan.md` case 14 (a 65538-byte result),
per `BACKLOG.md`'s `PORT32-01` scope (read from `88ac973`).

## Stack allocation path (structural, not measured here)

`struct cb_program_v1.requested_stack_size` (`include/cannedbsd/abi.h:236`)
is a plain `size_t`; `0` means "use the default":

```c
// src/executor.c:179-183
size_t stack_size = program->descriptor.requested_stack_size;
if (stack_size == 0) stack_size = 64 * 1024;
native->context = task->kernel->host->context_create(
    native_entry, native, stack_size);
```

`context_create` is host-specific. **Linux** (`src/host_linux.c:56-80`)
uses `malloc(stack_size)` directly as the `ucontext` stack; this
project's own code reserves nothing from it, but this audit does not
have a reliable, reviewed measurement of what the C library's own
`makecontext`/`swapcontext` implementation itself consumes before task
code runs (an earlier attempt at measuring this directly was itself
methodologically unsound -- see below -- and is retracted, not
replaced). **Mac** (`platform/mac68k/host_mac.c:185-203`) allocates
`stack_size + 4` bytes and places an initial machine-context frame `56`
bytes below the top of that buffer
(`platform/mac68k/context.S:5-17,20-24`); how much of that 56 bytes
remains permanently unavailable to task code, versus how much the
`movem`/`rts` sequence reclaims before `context_entry` starts, is a
real question this audit raised but does not resolve with confidence
here -- it needs the same real, linked measurement `HEAD-01` should
do, not a hand-trace of the assembly alone. Neither host detects stack
overflow at runtime; this audit does not propose adding detection.

## Exploratory `-fstack-usage` observations -- host-header compiles, not project frames

The pinned `head.c` (`char buf[65536];` at line 145) was compiled
standalone with `-fstack-usage` on two real toolchains reachable over
SSH/Docker on the CI runner host: the pinned Retro68 image
(`ghcr.io/autc04/retro68@sha256:459dd3ea9856262162615527021be7b64f198631dc59cca8cedbf197b7656019`,
`m68k-apple-macos-gcc` 16.1.0, `-Os` matching
`platform/mac68k/CMakeLists.txt`) and the pinned CI agent image
(`tribblix-woodpecker-agent:3.18.0`, Alpine 3.22.5, `cc` = GCC 14.2.0,
`-O2` matching this project's own default `CFLAGS`).

**These compiles used host libc headers (`unistd.h`, `stdio.h`, etc.)
plus a minimal `-include` shim for the handful of declarations an
isolated, unlinked single-file compile still needed
(`getprogname`, `__dead`/`__COPYRIGHT`/`__RCSID`) -- they did not pass
`-Ilibc/include -Icompat/netbsd/include` or any of this project's own
private headers.** That means `getopt`/`optarg`/`strtoimax`/etc.
resolved against the *host's* declarations in this compile, not this
project's private veneers. Although a function call's effect on its
*caller's* own frame size is generally insensitive to which
declaration of the callee it links against, this was not verified, and
the compiles are therefore **exploratory, host-header isolated
compiles, not a measurement of this project's own build**. Retained
here for whatever value they have, with that limitation stated
plainly, not hidden:

```
$ cat shim.h    # Mac
#define __dead __attribute__((noreturn))
const char *getprogname(void);
$ m68k-apple-macos-gcc -std=c99 -Os -ffunction-sections -fdata-sections \
    -Wall -Wextra -fstack-usage -include shim.h -c head.c -o head.o
head.c:143:1:head    65584    dynamic,bounded
head.c:71:1:main     80       dynamic,bounded
```

```
$ cat shim.h    # Linux (Alpine, inside the pinned CI agent image)
const char *getprogname(void);
$ cat sys/cdefs.h
#define __COPYRIGHT(x)
#define __RCSID(x)
#define __dead __attribute__((noreturn))
$ cc -std=c99 -D_XOPEN_SOURCE=700 -O2 -fstack-usage \
    -I. -include shim.h -c head.c -o head.o
head.c:143:1:head.part.0    65600    static
head.c:143:1:head           32       static
head.c:71:1:main             96       static
```

**Also corrected**: an earlier version of this note summed `head`'s
32 bytes and `head.part.0`'s 65600 bytes as simultaneously live,
treating the split as an ordinary call. Independent review examined
the actual object code and found `head`'s 32-byte stub pops its own
saved registers and *tail-calls* (jumps, not calls) into
`head.part.0` -- releasing its own frame first, not keeping both live.
This audit did not re-verify that disassembly itself (no further
measurement was taken for this revision, per direction) but accepts
and records the correction: the two figures are not additive.

**No peak, minimum, residue, or headroom number is claimed from any of
the above.** A single-file host-header compile's per-function
`-fstack-usage` output is a real data point about the pinned source's
own local-variable footprint, but is not a substitute for compiling
the real, private-header build and measuring or running it -- that is
explicitly `HEAD-01`'s own job, not this audit's.

## An earlier Linux `ucontext` measurement is retracted, not corrected

An earlier revision claimed to measure the `ucontext` bootstrap's stack
cost at "9 bytes" by filling a stack buffer with a `0xAA` sentinel,
calling `getcontext`/`makecontext`/`swapcontext`, and scanning from the
top of the buffer for the first non-sentinel byte, **stopping at the
first mismatch**. Independent review correctly pointed out that
stopping at the first mismatch only finds the *offset of the
highest-address touched byte from the top of the buffer* -- it does
not establish that everything between that byte and the top was
actually touched, and does not establish "stack usage" or "permanent
residue" in any sense that arithmetic can safely be built on. That
number is removed from this note entirely, not merely reframed; this
audit makes no numeric claim about the Linux `ucontext` bootstrap's
cost.

## RAMFS: allocator ceiling and peak-memory arithmetic (confirmed correct)

`src/ramfs.c`'s growth path (`api_write`'s callers, lines `418-458`)
doubles capacity with no ceiling of its own below `SIZE_MAX`. On Mac,
`host_allocate`/`host_resize` (`platform/mac68k/host_mac.c:109-114,
127-140`) reject any single allocation above `INT32_MAX`, and
`host_resize` allocates the *new*, larger buffer, copies the old data
into it, and only then releases the old buffer -- both are briefly
live simultaneously during that copy.

For a 65538-byte file, `src/ramfs.c`'s doubling sequence (`64, 128,
..., 65536, 131072`) settles at **131072 bytes final capacity** per
file, since `65536 < 65538`. This audit's proposed fixture needs an
input file (settled at 131072 bytes by the time the child runs) and an
output file growing to the same final size. At the single moment the
*output* file's own last doubling step (`65536 -> 131072`) is in
progress, the combined live RAMFS data is:

**131072 (input, settled) + 65536 (output, old buffer, not yet
released) + 131072 (output, new buffer, mid-copy) = 327680 bytes**,

before any struct/VFS-node metadata or task stacks. This is a real,
bounded, computable number, not a proposal to change RAMFS's own
growth algorithm or raise any ceiling -- no runtime expansion is
requested. The implementing fixture must check `host_allocate`/
`host_resize`/`cb_resize`'s return values for allocation failure
explicitly and treat it as a real, handled outcome; whether 327680
bytes plus the rest of a booted guest's own footprint fits the
Basilisk II guest's actual configured heap is a genuinely pending,
coordinator-owned measurement, not claimed here.

## Descriptor redirection: existing APIs, correctly described

`struct cb_spawn_action_v1`/`CB_SPAWN_DUP2`/`CB_SPAWN_CLOSE`
(`include/cannedbsd/abi.h:74-84`) and `api->stat`/`struct cb_stat_v1`
(`abi.h:65-72`) are already declared and exercised by an existing,
directly analogous test. `CB_SPAWN_CLOSE`/`CB_SPAWN_DUP2` actions apply
to the *child's own* descriptor table during spawn setup
(`src/core.c:571-586`) -- the parent must separately call `api->close()`
on its own copies, exactly as the existing precedent already does:

```c
// tests/test_core.c:3090-3106 (stdioepipeprobe_main)
if (api->pipe(descriptors) < 0) return 234;
if (api->close(descriptors[0]) < 0) return 235;   // parent's own close, before spawn
...
actions[0].type = CB_SPAWN_DUP2;   // duplicates into the CHILD
actions[1].type = CB_SPAWN_CLOSE;  // closes in the CHILD, not here
...
if (api->spawn("stdioprobe", child_argv, envp, actions, 3, &child) < 0) return 236;
if (api->close(descriptors[1]) < 0) return 237;   // parent's own close, after spawn
```

## Proposed fixture: one portable probe, both platforms (confirmed correct)

A `head`-exercising probe should spawn `head -c 65538` with its stdin
and stdout redirected (via `CB_SPAWN_DUP2`, exactly like the pattern
above) to opened RAMFS files, `api->stat` the output file to confirm
`size == 65538` without reading it, then `api->read` it back in bounded
chunks (e.g. 4096 bytes at a time) confirming every byte and the total
length -- never holding the full 65538 bytes in one buffer. It prints
only a short, fixed result on success, exactly like every other
existing probe (`libcbasenameprobe`, `libcstrtoimaxprobe`, etc.), so it
fits the existing 4096-byte Mac capture ceiling regardless of the
65538-byte content it verifies internally -- the harness's own
captured-output comparison limits what a probe *prints*, not what it
*checks*. This is `HEAD-01-testplan.md`'s own case-14 requirement,
satisfied with one design registered on both Linux (its own new scoped
fixture, mirroring `FIXTURE_CONV`/`FIXTURE_YES`, not `FIXTURE_FULL`)
and Mac (`platform/mac68k/CMakeLists.txt`/`main.c`/
`acceptance_cases.def`, exactly like every other probe already listed
there). Not implemented here.
