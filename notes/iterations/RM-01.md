## What changed since FILEUTIL-01

`FILEUTIL-01` (pre-`FTS-CORE-01`) reported `rm` as "blocked on subsystem:
fts only," because a fatal missing-header error at `#include <fts.h>`
(line 53) stops the compiler before anything past it is reached. That was
correct evidence for what it measured, but it is not a prediction about
what happens after `fts.h` exists — I re-ran the compile now that it does,
per direction, rather than assume the prediction still holds. It does not:
there is a second, larger blocker past it.

## Method

Same technique as `FILEUTIL-01` and `FTS-CORE-01`: `alpine:3.22` container,
`apk add build-base`, compiled against this project's own headers only:

```sh
cc -D_XOPEN_SOURCE=700 -Iinclude -Isrc -Icompat/netbsd/include -Ilibc/include \
   -std=c99 -Wall -Wextra -Wpedantic -c upstream/netbsd/bin/rm/rm.c -o /tmp/rm.o
```

(`-Icompat/netbsd/include` added because that is where `sys/param.h`'s
`MIN()`-only import shim already lives for `dirname.c`/`basename.c`/
`strtoimax.c` — confirmed by reading `compat/netbsd/include/sys/param.h`
and the Makefile rules for those three files; omitting it would measure a
stricter, non-representative environment that doesn't match how this
project's own Makefile actually compiles pinned imports.) `-Werror` was
dropped for this pass specifically to see everything in one sweep, matching
`FILEUTIL-01`'s own `cat.c` methodology, which listed eleven issues from one
compile rather than fixing and re-running eleven times.

## Findings, categorized

### Resolved by FTS-CORE-01

`#include <fts.h>` and every `fts_open`/`fts_read`/`fts_close`/
`fts_set(FTS_SKIP)` call site in `rm_tree()` now resolve cleanly against
`libc/include/fts.h`. `FTS_DNR`/`FTS_ERR`/`FTS_NS`/`FTS_D`/`FTS_DP`/`FTS_W`
all exist with the values `rm.c` switches on.

### New, real blocker: `struct stat` is STAT-02's territory, not RM-01's

`rm_file()` — the plain, non-recursive path taken by *any* invocation of
`rm` on an ordinary file, unconditional on every flag — calls
`lstat(f, &sb)` and then `S_ISDIR(sb.st_mode)` before doing anything else.
`libc/include/sys/stat.h` is still the two-line stub `FILEUTIL-01` found
for `cat`. This is not a new discovery in the abstract (my own
`notes/iterations/FTS-CORE-01.md` already flagged `struct stat` as "CAT-01's
still-open decision"), but concretely: `BACKLOG.md`'s `STAT-02` entry
(added in `69f5f19`, status **Ready; unassigned**) already scopes exactly
this — "wire the existing runtime `stat`/`fstat` through a real POSIX
`struct stat`... synthesizing POSIX type bits (`S_IFREG`, `S_IFDIR`,
`S_IFCHR`, `S_IFIFO`) from `cb_node_type`... deliberately does NOT grow
`cb_stat_v1`." That scope, once done, covers `S_ISDIR` (needed
unconditionally) and `S_ISREG` (needed by the deferred `-P` path) directly.

Implementing a second, RM-01-local `struct stat` here would either
duplicate `STAT-02`'s work or produce a conflicting shape for whoever picks
it up next — the same category of risk `FS-STAT-01`'s "one unified append"
decision was written to avoid for `cb_stat_v1` itself. **Recommendation:
`RM-01` now depends on `STAT-02`, in addition to the already-satisfied
`FTS-CORE-01`.** `lstat`/`fstat` themselves (the function wrappers, as
opposed to the type they fill in) are not currently public either — `stat`
is public now (`cb_libc_stat`, added for `FTS-CORE-01`) but there is no
`lstat`/`fstat` wrapper; RAMFS has no symlinks (confirmed earlier this
session), so `lstat`'s behavior on this backend is identical to `stat`'s —
that part is trivial once `STAT-02`'s type exists to return.

### Small, independent gaps — RM-01's own scope, not STAT-02's

Confirmed by the same compile pass, none touching `struct stat`:

1. **`strrchr`** (`string.h`) — `checkdot()`'s trailing-slash-trim and
   basename-extraction logic, called unconditionally in `main()` before any
   flag branching. Exactly the gap `FILEUTIL-01` found in `rmdir.c` and
   Ryan moved to this ID's budget; confirmed independently present in
   `rm.c` too.
2. **`memset`** (`string.h`) — used only inside the `-P` overwrite macros
   (`WRITE_PASS`/`READ_PASS`); previously unlisted because the audit never
   reached this file's `-P` code before. Deferred along with `-P` itself
   (see below), but the *declaration* still needs to exist for the file to
   parse — real BSD's `memset` is trivial to add to the existing
   `string.h` veneer regardless of whether `-P` is ever exercised.
3. **`getchar`** (`stdio.h`) — `check()`'s y/n prompt reader. Needed for
   `-i` to actually work, not just to compile.
4. **`__unused`** (`sys/cdefs.h`) — attribute macro on `progress(int sig
   __unused)`. `__dead` already exists in this file (added for a prior
   import); `__unused` does not. Without it the file fails to *parse*
   (not just link/type-check) regardless of whether `-P`/`SIGINFO`/`-W`
   are ever reached at runtime — real BSD's shape is
   `__attribute__((__unused__))`, trivial to add alongside `__dead`.
5. **`unlink`, `rmdir`** (`unistd.h`) — the actual removal calls. `VFS-04`
   already added `api->unlink`/`api->rmdir` at the raw runtime layer, and
   `api->unlink` already has a public path in some form (used inside
   `cb_libc_opendir`'s own error paths per earlier `FIXTURE_DIRENT`
   evidence), but there is no POSIX-named public `unlink()`/`rmdir()`
   libc-consumer function yet. Same shape as `FTS-CORE-01`'s
   `cb_libc_stat`: thin pass-throughs, no new ABI.

### Deliberately out of scope, matching "permissions enforcement deferred"

Ryan's direction to scope `-f`/`-i` "to what exists" maps onto exactly the
branch structure `check()` and `rm_overwrite()` already have:

- **`check()`'s non-`-i` branch** (the "ask if the file is unwritable and
  we're on a terminal" heuristic) needs `access()`, `W_OK`, `ETXTBSY`,
  `S_ISLNK`, `strmode()`, `user_from_uid()`, `group_from_gid()` — a real
  passwd/group database and permission model this project doesn't have.
  The `-i` branch itself needs none of these; it only needs `getchar()`
  (above) and a `fprintf`. Scoping `-i` to *only* the explicit-flag branch,
  and never reaching the auto-ask heuristic in tests, is the natural cut.
- **`-P`** (secure overwrite): `O_SYNC`, `O_RSYNC`, `O_NOFOLLOW`,
  `arc4random`, `fsync`, `sync`, `lseek`, `u_int32_t`, and `S_ISREG`
  (itself gated on `STAT-02`). Out of scope; `rm -P` documented as outside
  the accepted matrix, matching `FCNTL-01`'s precedent for `cat -l`.
- **`-W`** (whiteout): `S_ISWHT`, `S_IFWHT`, `undelete()`. RAMFS has no
  whiteout concept at all (same conclusion `FTS-CORE-01`'s design reached
  for `FTS_WHITEOUT`). Out of scope; `rm -W` documented as outside the
  accepted matrix.
- **`SIGINFO`/`signal()`**: BSD-specific, no POSIX `signal()` veneer
  exists yet (`libc/include/signal.h` is absent). The progress-on-SIGINFO
  feature is cosmetic (`^T` status reporting); out of scope. `main()`'s
  `signal(SIGINFO, progress)` call itself still needs *something* to
  compile against — see below.

All five of these still need to *compile* (byte-for-byte import, unmodified
source) even though their behavior is out of scope for the accepted matrix.
Where a real implementation isn't warranted, the plan is a declaration-only
or honestly-failing stub (matching `FCNTL-01`'s and `FTS-CORE-01`'s own
precedent for `FTS_XDEV`), not a stub that silently claims success it can't
back up. `signal()` itself is the one piece here I have not yet scoped a
plan for — it needs its own small design note once `STAT-02` unblocks the
rest, since a `signal()` that only ever accepts `SIGINFO` and does nothing
real is a different kind of claim than the `-P`/`-W`/`-i`-heuristic stubs
above (those are *declarations for compilation*; `signal()` is a *function
call that must behave sanely for whatever gets registered against it*, even
if `SIGINFO` itself never fires on this platform).

Everything needed to make the file compile *in full* (byte-for-byte,
including code paths outside the accepted matrix) is now in place:
`S_IFWHT`/`S_ISWHT` (`sys/stat.h`), `st_uid`/`st_gid`/`st_dev` added to
the plain (non-ABI-versioned) `struct stat` as explicit, arbitrary-zero
sentinels matching STAT-02's own precedent for `st_blksize`/`st_blocks`,
`lseek`/`fsync`/`sync` (real, honest implementations: RAMFS genuinely has
nothing to flush, so success is a true fact, not a claimed capability),
`arc4random`/`access`/`undelete`/`strmode`/`user_from_uid`/
`group_from_gid` (honest for what they are: a non-cryptographic PRNG
unreachable via the accepted matrix, a real existence check reframed
below, a real ENOSYS failure for a whiteout concept that doesn't exist,
a real minimal permission-string formatter, and real BSD's own
documented numeric-ID fallback for every uid/gid since no passwd/group
database exists here at all), `O_SYNC`/`O_RSYNC`/`O_NOFOLLOW`
(deliberately-unrecognized `open()` flag bits, rejected with `EINVAL` by
`cb_libc_open`'s existing flag validation --  `rm -P`'s `open()` call
fails immediately, before `arc4random`/`fsync`/`lseek` inside its macros
are ever reached), and `signal()`/`SIGINFO` (a provisional, explicitly-
labeled placeholder that always fails and never installs anything --
SIG-01's own note explicitly excludes "the private signal.h veneer...
and arbitrary handlers" from its scope, so there is nothing real to wire
this to yet; this is flagged as its own open question below, not
resolved here).

**One real behavioral bug found and fixed via smoke-testing, not left as
a stub:** an initial `access()` implementation returning `-1`/`ENOSYS`
unconditionally made `check()`'s "ask before removing an unwritable
file" heuristic fire on *every* plain `rm` of an ordinary file (cannedBSD's
own virtual console always reports `isatty(STDIN_FILENO)` true,
regardless of the host's real stdin, so `check()`'s `!stdin_ok`
short-circuit this note originally assumed would make that branch
unreachable does not apply). Since RAMFS never enforces mode bits for
any operation, "is this writable" is truthfully "yes, for anything that
exists" on this backend -- `access()` now checks existence via
`bound_api->stat` and returns success for anything found, which is an
honest description of this runtime's real behavior, not a false claim.

## A second, larger finding: VFS-03's directory-iteration cursor breaks under `rm -r`'s own access pattern

While testing `rm -r` on a tree with more than one entry per directory,
an entire subtree (and its contents) silently failed to be removed,
surfacing as "directory not empty" on the top-level `rmdir()`. This is
**not a bug in FTS-CORE-01 or in this ID's own new code** -- it is a
real, load-bearing gap in `VFS-03`'s own already-accepted design.

`notes/iterations/VFS-03-design.md` §2 explicitly, deliberately chose
`child_at`'s `index` parameter to be "an ordinal position...re-walked
from `directory->children` on every call," and explicitly rejected
retaining a cursor node and advancing via its own `next_sibling`,
specifically because `ramfs_unlink` clears a removed node's own
`next_sibling` to `NULL`. The design note goes on to explicitly accept,
and test (§7 items 4a/4b), that a concurrent removal skips a sibling and
a concurrent insertion duplicates one, framing this as within what POSIX
already permits for a generic external mutator racing an iterator.

That framing does not survive contact with `rm -r`'s own access pattern,
because it is not a generic external race: it is the *same task*,
through the *same open directory handle*, deliberately removing the
entry it just visited before asking for the next one. Concretely, for a
directory `[top, a]` (RAMFS prepends, so `top` -- added after `a` -- is
first): `readdir()` returns `top` at index 0; `rm` unlinks `top`,
shrinking the list to `[a]`; `readdir()` advances to index 1, which
`child_at` now finds does not exist, reporting a false end of directory.
`a` (and its entire subtree) is never visited, never removed, and the
top-level `rmdir()` then correctly reports `ENOTEMPTY` on the leftover
directory it never processed.

Real filesystems do not hit this for exactly this pattern because their
directory representations use a stable byte/block offset as the
`readdir()` cursor, which does not shift when the entry at the *current*
position is removed (only genuinely concurrent, unrelated mutations by
other processes can perturb it, and even then differently). RAMFS's
singly-linked, position-recomputed-from-head representation shifts
immediately. `VFS-03`'s design note reasoned carefully about generic
concurrent mutation with no consumer that needed self-deletion-during-
iteration to exist yet -- `rm -r` (and, later, any recursive `cp`/`mv`)
is exactly that consumer, and it is close to the canonical reason
`fts(3)`/recursive removal exists as a subsystem at all.

**Not fixed under this ID.** This is a considered, documented,
already-accepted design decision, not an oversight bug -- reopening it is
not RM-01's call to make unilaterally, unlike the earlier `access()` fix
above (a plain implementation gap in this ID's own new code) or
`VFS-04`'s rename-cycle bug (an unintentional gap nobody had reasoned
about). A candidate direction worth putting in front of whoever does own
this: a *look-ahead* cursor (capture the current entry's own next-sibling
identity *before* returning the current entry to the caller, in the same
`readdir()` call, rather than deferring that lookup to the following
call) sidesteps the specific hazard the design note rejected the naive
"retain and advance later" version for, since it never reads
`next_sibling` on a node after that node may have already been unlinked.
This would need a new, `struct_size`-guarded `next_sibling` node op
(RAMFS's own field of that exact name makes the backend implementation
trivial) and retain/release discipline on the looked-ahead node across
the gap between two `readdir()` calls. Offered as a starting point for
the design conversation, not as a fix already built or validated here.

**Test-matrix consequence:** the accepted `-r` test tree is deliberately
single-child-per-level (see the comment on `rm01cmdprobe_main` in
`tests/test_core.c`), which cannot trigger the skip (nothing exists after
position 0 to skip past). This proves `rm_tree()`'s own `FTS_D`/`FTS_DP`
pre/post-order dispatch and `unlink()`/`rmdir()` sequencing are correct
in isolation, while being honest that multi-entry-directory `-r` is a
known, currently-broken case pending this decision, not part of the
tested/accepted matrix yet.

## A third, smaller bug found and fixed in FTS-CORE-01 itself

`rm -rf` on a missing top-level path was incorrectly exiting `1` instead
of `0` (violating `-f`'s "ignore non-existent files" contract). Root
cause: `cb_libc_fts_read`'s clean end-of-walk `return NULL` never cleared
`errno`, so `errno` from an internally-handled `FTS_NS` entry (the
missing path, already correctly classified and left for `rm_tree()`'s
own `NONEXISTENT(errno) && fflag` check to silently skip) was still set
when the loop ended. `rm.c`'s own tail check, `if (errno) err(1,
"fts_read")`, has no errno reset of its own -- it relies entirely on
`fts_read()` guaranteeing errno reflects only a genuine fts-level failure
on a clean `NULL` return, never leftover state from an already-reported
per-entry condition. This is squarely FTS-CORE-01's own bug (a real gap
in a documented `fts(3)` contract detail this design note did not
previously call out), not VFS territory -- fixed directly: `errno = 0`
immediately before the "no more roots" `return NULL`, leaving the
separate allocation-failure `return NULL` path (which must preserve
`ENOMEM`) untouched.

## Status

`rm` is implemented, registered (`commands/rm_module.c`, base program
table), and byte-for-byte pinned `rm.c` compiles and links in full. The
accepted matrix -- plain `rm`, `-f`, `-i`, `-d`, `-v`, `-r` on a
single-child-per-level tree, `checkdot()`'s `.`/`..` rejection -- is
implemented, tested (`FIXTURE_RM01`'s `rm01cmdprobe` plus the five
independent-gap probes), and green under `make ci` on both compilers.

Two things are explicitly NOT resolved here, both flagged above for the
coordinator rather than decided unilaterally:

1. **`-r` on a multi-entry directory is known-broken**, pending a
   decision on VFS-03's directory-iteration cursor design (see above).
2. **`signal()`/`SIGINFO` is a provisional placeholder** (always fails,
   installs nothing) pending a decision on whether/how to wire `rm`'s
   `-v`/`^T` progress reporting to SIG-01's internal interrupt core, per
   director instruction not to resolve that design question under this
   ID.

`-P` (secure overwrite) and `-W` (whiteout) remain documented outside the
accepted matrix, matching the `FCNTL-01`/`cat -l` precedent: they compile
and fail immediately and honestly (`EINVAL` from unrecognized `open()`
flags, `ENOSYS` from `undelete`) rather than claiming a capability this
backend does not have.
